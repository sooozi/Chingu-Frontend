# 03. 성능 최적화 (Performance)

리팩토링 이후 기능이 좋아졌더라도 **서비스가 느려지면 사용자 경험이 크게 악화**된다.  
이 문서는 리팩토링 과정에서 성능 저하를 방지하고, 개선 포인트를 체크하기 위한 **성능 기준 문서**이다.

---

## 1) 핵심 목표

- 불필요한 리렌더링을 줄여 **UI 반응성**을 유지한다.
- 이미지/에셋 최적화를 통해 **초기 로딩 속도**를 개선한다.
- 번들 크기를 관리하여 **배포 파일 용량 증가를 방지**한다.
- 리팩토링 후에도 성능이 유지되는지 **지표로 검증**한다.

---

## 2) 최적화 기준 (핵심 3가지)

### 2-1. 렌더링 횟수 최적화

React에서 렌더링은 컴포넌트가 다시 실행되어 UI를 다시 그리는 과정이다.  
불필요한 리렌더링이 많아지면 입력 지연, 스크롤 끊김 등의 문제가 발생할 수 있다.

✅ 개선 방향

- `React.memo`를 통해 불필요한 자식 컴포넌트 리렌더링을 방지한다.
- `useMemo`를 통해 계산 비용이 큰 값을 캐싱한다.
- `useCallback`을 통해 함수 재생성을 줄이고 props 변경을 최소화한다.

---

### 2-2. 이미지 및 에셋 최적화

이미지/폰트/아이콘 같은 정적 에셋은 초기 로딩 속도에 큰 영향을 준다.  
크기가 큰 리소스는 네트워크 비용과 렌더링 비용을 증가시켜 성능 점수를 떨어뜨린다.

✅ 개선 방향

- 불필요하게 큰 이미지 사용을 피하고, 적절한 해상도로 최적화한다.
- 가능하면 `webp` 같은 효율적인 포맷을 사용한다.
- `Lighthouse`를 통해 성능 점수를 확인하고 개선 포인트를 점검한다.

---

### 2-3. 번들 크기 관리

번들 크기는 사용자가 최초로 다운로드해야 하는 코드의 양이다.  
번들이 커지면 초기 진입 속도와 실행 속도가 느려질 수 있다.

✅ 개선 방향

- 사용하지 않는 라이브러리/코드(Dead Code)를 제거한다.
- 필요한 페이지에 한해 코드 스플리팅(`React.lazy`)을 적용한다.
- 특정 페이지/기능이 초기 진입에 필요 없는 경우 “나중에 로드”하도록 분리한다.

---

## 3) 권장 최적화 구조 (적용 위치)

### 3-1. Page/Container

- 페이지 단위에서 코드 스플리팅(지연 로딩) 적용 검토
- 쿼리/상태 변경으로 인한 전체 리렌더링 감시

✅ Page는 “무거운 렌더링 구조가 생기지 않게” 관리한다.

---

### 3-2. View (UI 컴포넌트)

- props 변화에 민감한 컴포넌트는 `React.memo` 적용 검토
- 리스트 아이템/카드 UI는 최소 렌더링을 목표로 한다

✅ View는 “불필요한 리렌더링이 발생하지 않게” 설계한다.

---

### 3-3. Custom Hook

- `useMemo`, `useCallback`을 필요한 경우에만 적절히 사용한다
- 연산이 큰 값은 Hook에서 계산 후 View로 전달한다

✅ Hook은 “비싼 계산/함수 재생성”을 조절한다.

---

### 3-4. Assets (이미지/폰트/아이콘)

- 큰 이미지 사용 금지
- 폰트/아이콘은 필요한 것만 사용한다

✅ Assets는 “가볍게 유지”한다.

---

## 4) 성능 규칙 (Performance Rule)

### 허용되는 방향 ✅

- 필요한 경우에만 `memo`, `useMemo`, `useCallback` 적용
- 초기 진입에 필요 없는 화면은 `React.lazy`로 분리
- 이미지/에셋은 최적화 후 사용

### 금지되는 방향 ❌

- 모든 컴포넌트에 무작정 `React.memo` 적용
- `useMemo/useCallback`을 습관적으로 남발
- 용량이 큰 이미지 원본을 그대로 사용
- 사용하지 않는 라이브러리를 계속 유지

---
