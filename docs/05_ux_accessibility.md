# 05. 사용자 경험(UX) 및 접근성 (UX & Accessibility)

리팩토링 과정에서 기능이 정상 동작하더라도  
**에러/로딩/접근성 처리**가 부족하면 사용자는 서비스가 불안정하다고 느낀다.

이 문서는 리팩토링 이후에도 사용자 경험이 무너지지 않도록  
UX 품질과 접근성을 유지하기 위한 **점검 기준 문서**이다.

---

## 1) 핵심 목표

- API 실패 상황에서 사용자에게 **명확한 피드백**을 제공한다.
- 데이터 로딩 중에도 화면이 멈춘 것처럼 보이지 않도록 **로딩 상태를 표현**한다.
- 기본 웹 접근성 규격을 준수하여 **누구나 사용 가능한 UI**를 제공한다.
- 리팩토링 후에도 UX가 유지되는지 **체크리스트로 검증**한다.

---

## 2) 점검 기준 (핵심 3가지)

### 2-1. 에러 핸들링 (Error Handling)

API 호출 실패 / 권한 오류 / 서버 오류 등 예외 상황에서  
사용자가 현재 상태를 이해할 수 있도록 적절한 피드백이 필요하다.

✅ 개선 방향

- API 실패 시 토스트 메시지, 에러 메시지, 에러 페이지 등으로 안내한다.
- 재시도 가능한 경우 “다시 시도” 버튼 또는 retry 로직을 제공한다.
- 사용자 잘못이 아닌 경우(서버 오류 등) 책임감을 주는 문구를 피한다.
  - 예: “잘못 입력하셨습니다” ❌
  - 예: “일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요.” ✅

---

### 2-2. 로딩 상태 (Loading State)

데이터를 가져오는 동안 화면이 비어 있으면 사용자에게 “멈춘 화면”으로 보일 수 있다.  
따라서 로딩 중임을 명확히 보여줘야 한다.

✅ 개선 방향

- 목록/카드 UI는 Skeleton을 우선 적용한다.
- 단순 액션 처리(버튼 클릭 등)는 Spinner 또는 버튼 disabled로 처리한다.
- 로딩 중 중복 클릭을 방지한다. (버튼 비활성화, submit 중복 방지)

---

### 2-3. 웹 접근성 (Web Accessibility)

기본 접근성 규칙을 준수하면 키보드 사용자/스크린리더 사용자도 서비스 이용이 가능하며  
전반적인 UX 완성도 또한 함께 개선된다.

✅ 개선 방향

- 이미지에는 의미 있는 `alt` 속성을 제공한다.
- 아이콘만 있는 버튼에는 `aria-label`을 제공한다.
- 버튼/링크 요소는 키보드(tab)로 접근 가능해야 한다.
- 클릭 가능한 영역은 `div`보다 `button`을 우선 사용한다.

✅ 추가 점검 항목 (권장)

- 입력 요소(input/textarea/select)는 `label`과 연결한다. (`htmlFor` / `id`)
- 폼 에러 메시지는 스크린리더가 인지할 수 있도록 `role="alert"` 또는 `aria-live` 적용을 검토한다.
- 에러 상태의 입력 요소에는 `aria-invalid`를 적용하고, 에러 메시지와 `aria-describedby`로 연결한다.
- 모달/다이얼로그는 포커스 이동 및 키보드 조작을 보장한다.
  - 열릴 때 포커스를 모달 내부로 이동
  - 닫힐 때 포커스를 원래 트리거 버튼으로 복귀
  - `ESC`로 닫기 지원
- 색상만으로 상태를 전달하지 않는다. (텍스트/아이콘 등 추가 정보 제공)
- 장식용 이미지(의미 없는 이미지)는 `alt=""`로 처리하여 불필요한 읽기를 방지한다.
- 클릭/터치 가능한 요소는 충분한 크기의 영역을 확보한다. (모바일에서 누르기 쉬운 크기)
- 제목(heading)은 `h1 → h2 → h3` 순서를 자연스럽게 유지하여 문서 구조를 명확히 한다.

```tsx
## 4) 접근성 체크리스트 (PR 리뷰 기준)
- [ ] 이미지 `alt`가 누락되지 않았는가?
- [ ] 아이콘 버튼에 `aria-label`이 제공되는가?
- [ ] input이 `label(htmlFor/id)`과 연결되어 있는가?
- [ ] 키보드(Tab)만으로 주요 기능을 사용할 수 있는가?
- [ ] 클릭 가능한 요소를 `div` 대신 `button/link`로 구현했는가?
```
