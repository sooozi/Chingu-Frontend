## 1. 네이밍 규칙 적용 (Intent 중심)
> 원칙: “handle~” 남발 금지, 도메인 기반 동사+목적어

- [ ] 의미가 약한 이름 식별 및 교체
  - [ ] `handleClick`, `doSomething`, `data/temp/value`, `fn/a/b` 제거
- [ ] 함수 네이밍을 “동사 + 목적어”로 정리
  - [ ] 조회: fetch/get/load
  - [ ] 생성: create/add
  - [ ] 변경: update/set/patch
  - [ ] 삭제: remove/delete
  - [ ] 검증: validate
  - [ ] 변환: parse/map/format
- [ ] Boolean 네이밍을 질문형으로 통일
  - [ ] `open/error/submitable` → `isOpen/hasError/canSubmit`
- [ ] 네이밍 변경으로 인해 파생된 export/import 변경은 최소화(불가피한 범위만)

## 2. 매직 넘버 / 매직 스트링 제거
> 원칙: “의미 있는 리터럴은 상수화”, “문자열 상수는 타입과 함께”

### 2-1) 의미 있는 리터럴 식별
- [ ] status/role/tab/pageSize/limit 등 의미 있는 값 찾기
- [ ] 조건문에 박힌 숫자/문자열(`status === 3`, `role === 'ADMIN'`) 찾기

### 2-2) 상수화 적용
- [ ] 상수 객체로 치환 (예: STATUS)
- [ ] 중복되는 LIMIT/pageSize가 파일마다 있으면 단일 상수로 통합(이번 PR 범위 내에서만)
- [ ] 문자열 상수는 `as const` + 타입 함께 정의
  - [ ] 예: `USER_ROLE` + `UserRole` 타입

### 2-3) UI 텍스트 관리(범위 제한)
- [ ] 버튼 라벨/에러 메시지가 여러 군데 흩어진 경우 1개만 선정
- [ ] `messages.ts` 또는 `copy.ts`로 이동 여부 판단
- [ ] 실제 이동은 이번 PR에서 수행할지 결정(무리하면 보류하고 메모)

## 3. 타입 안전성 강화 (TypeScript)
> 원칙: any는 최후, as 남발 금지(2회 이상이면 구조 의심)

### 3-1) any 제거 우선순위
- [ ] `any` 사용 위치 검색 및 목록화
- [ ] 가능한 경우 `unknown`으로 치환
- [ ] 타입 가드(또는 zod 스키마)로 안전하게 좁히기

### 3-2) as 캐스팅 점검
- [ ] `as` 사용 위치 검색
- [ ] 동일 파일에서 `as`가 2회 이상이면 리팩토링 후보로 표시
- [ ] 가능한 경우 타입 가드로 교체
  - [ ] 예: `if (!isUser(data)) return`

### 3-3) 타입 단일 출처 점검(이번 PR 범위 내)
- [ ] API 응답 타입이 여러 파일에 중복 정의되어 있는지 확인
- [ ] 이번 PR에서 건드린 타입만 단일 출처로 정리(과확장 금지)
  - [ ] `src/types/api.ts` 또는 `src/schemas/*.ts` 등 프로젝트 기준 경로로 이동 여부 판단

## 4. 함수 길이/책임 정리
> 원칙: 30줄 이상 분리, 중첩 줄이기, early return

### 4-1) 긴 함수 분리
- [ ] 30줄 이상 함수 1개 이상 식별
- [ ] “한 가지 일” 기준으로 내부 로직을 작은 함수로 분리
- [ ] 분리한 함수 이름은 의도 기반 네이밍으로 작성

### 4-2) 조건 분기 단순화
- [ ] 중첩 if/try-catch가 많은 구간 식별
- [ ] early return으로 평탄화
- [ ] 에러 처리 로직이 반복되면 작은 헬퍼로 분리(이번 PR 범위 내)

## 5. 마무리 확인 (Code Quality Gate)
- [ ] 네이밍 변경 후 “의도 추측”이 필요한 이름이 남아있는지 재검토
- [ ] 매직 넘버/스트링이 의미 단위로 상수화됐는지 확인
- [ ] any 0건 또는 감소했는지 확인 (불가피하면 사유 주석 남기기)
- [ ] as 캐스팅이 남아있다면 최소화/사유 설명
- [ ] 함수 책임이 분리되었는지 확인(30줄 이상/중첩 감소)
- [ ] TypeScript 에러/경고가 증가하지 않았는지 확인
- [ ] 리팩토링 전/후 동작 동일(수동 확인)
- [ ] 변경 사항 요약 3줄 작성 (PR 설명용)

## PR 완료 조건 (Gate)
- 의도 불명확 네이밍(의미 약한 이름) 주요 구간 제거
- 의미 있는 리터럴 상수화(매직 넘버/스트링 감소)
- any 최소화(가능하면 0)
- as 남발(2회 이상 반복) 제거 또는 구조 개선 근거 확보
- 긴 함수/중첩 분기 최소 1개 이상 개선
- 기능 동작 동일
